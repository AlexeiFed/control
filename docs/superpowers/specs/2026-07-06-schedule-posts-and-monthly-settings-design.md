# Дизайн: Операционные сутки по месяцам и Посты на объектах

## 1. Операционные сутки по месяцам

### Цель
Позволить настраивать время начала операционных суток (например, 08:00) для каждого объекта индивидуально на каждый месяц. Это необходимо, так как время пересменки может меняться от месяца к месяцу, и старые графики/табели не должны "поехать" при изменении настроек в новых месяцах.

### Архитектура БД
Создается новая таблица `object_monthly_settings`:
- `id` (uuid, primary key)
- `object_id` (uuid, foreign key to `security_objects`)
- `month` (text, формат 'YYYY-MM')
- `operational_day_start_time` (time)
- `UNIQUE (object_id, month)`

### Миграция данных
При создании таблицы необходимо перенести текущие значения `operational_day_start_time` из таблицы `security_objects` в новую таблицу `object_monthly_settings` для всех существующих объектов. Чтобы старые данные гарантированно не поехали, можно создать записи для текущего месяца и нескольких предыдущих (или при расчете, если записи нет, брать значение из `security_objects` как fallback).

### Изменения в UI
- На странице графика смен (где выбирается месяц) добавить элемент управления "Начало суток для этого месяца".
- При изменении этого значения сохранять его в `object_monthly_settings` для выбранного месяца.

### Изменения в логике
- Функции генерации сетки графика и расчета табеля должны принимать месяц как параметр и запрашивать `operational_day_start_time` из `object_monthly_settings`.
- Если для запрошенного месяца запись отсутствует, логика должна использовать значение предыдущего месяца или fallback значение из `security_objects`.

## 2. Посты на объектах

### Цель
Обеспечить возможность создания нескольких постов (разделов) на одном объекте. График и табель должны быть визуально разделены по этим постам, как показано на предоставленных скриншотах.

### Архитектура БД
1.  Создается таблица `object_posts`:
    - `id` (uuid, primary key)
    - `object_id` (uuid, foreign key to `security_objects`)
    - `name` (text, название поста)
    - `created_at` (timestamptz)
2.  В таблицу `shifts` добавляется колонка:
    - `post_id` (uuid, nullable, foreign key to `object_posts`)
3.  В таблицу `object_shift_templates` добавляется колонка:
    - `post_id` (uuid, nullable, foreign key to `object_posts`)
4.  В материализованную таблицу `timesheet_shift_entries` добавляется колонка:
    - `post_id` (uuid, nullable)
    - `post_name` (text, nullable)

### Миграция данных
Для существующих объектов, у которых уже есть смены, можно создать дефолтный пост (например, "Основной пост") и привязать к нему все существующие смены и шаблоны, чтобы сохранить целостность данных. Либо оставить `post_id` как `NULL` для старых смен и обрабатывать `NULL` как "Основной пост" в UI.

### Изменения в UI
- **Настройки объекта:** Добавить раздел управления постами (добавление, редактирование названия, удаление).
- **График смен:**
    - Если у объекта только один пост (или постов нет), отображать график как сейчас.
    - Если постов больше одного, визуально разделить сетку графика на секции (посты).
    - При добавлении/редактировании смены позволять выбирать пост (или автоматически привязывать к посту, в строке которого кликнули).
- **Табель:**
    - При отображении и экспорте табеля группировать строки по постам, выводя название поста как заголовок секции (согласно скриншоту 2).

### Изменения в логике
- Обновить запросы на получение смен и шаблонов, чтобы они включали информацию о посте.
- Обновить логику генерации табеля для поддержки группировки по постам.
